# Active-Directory-Enumeration-Lab
Active Directory enumeration lab using BloodHound,SharpHound,Powerview, and Splunk. Demonstrates offensive enumeration techniques and corresponding detection logs. 


Active Directory Enumeration Lab

Lab Overview

This lab demonstrates two enumeration approaches in an Active Directory environment:
	1.	Automated graph-based enumeration using BloodHound
	2.	Manual LDAP-based enumeration using PowerView

The objective was not only to perform enumeration, but also to analyze the telemetry and logging artifacts generated by each technique.

⸻

1️⃣ BloodHound Setup and Enumeration

1.1 Environment Preparation

The following components were installed:
	•	BloodHound (Legacy .exe version)
	•	Neo4j Community Edition
	•	OpenJDK 11 (required for Neo4j runtime)
	•	SharpHound v1.1.1

Version Compatibility Note

SharpHound and BloodHound versions must be compatible.

If mismatched, importing collected data into BloodHound may result in:

“Bad JSON file” error

This typically occurs when:
	•	The SharpHound collector version does not align with the BloodHound GUI version.
	•	The generated data schema does not match the expected format.

⸻

1.2 Data Collection with SharpHound

SharpHound was executed from a domain-joined machine using a domain user account.

⚠ SharpHound must be run in the security context of a domain user to successfully query Active Directory via LDAP.

Command Used: SharpHound.exe -c All

Explanation:
	•	-c All → Executes all available collection methods:
	•	Group membership
	•	ACLs
	•	Sessions
	•	Trusts
	•	Local admin relationships
	•	Object properties

SharpHound performs enumeration primarily through:
	•	LDAP queries
	•	SMB session enumeration
	•	Active Directory object queries

⸻

1.3 Data Import

The generated ZIP file was uploaded into BloodHound.

BloodHound uses:
	•	Neo4j as its graph database backend
	•	Cypher queries to identify privilege escalation paths

⸻

1.4 Telemetry Observed

During SharpHound execution:
	•	Event ID 4662 (An operation was performed on an object) was observed.
	•	This indicates LDAP-based directory object access.
	•	Enumeration activity touched Active Directory objects on the Domain Controller.

This demonstrates that automated enumeration leaves detectable LDAP access traces.

⸻

2️⃣ Manual Enumeration Using PowerView

2.1 Execution Context

Manual enumeration was performed from a domain-joined machine using a domain user account.

An older version of Powerview.ps1 was used 
This version primarily relies on:
	•	.NET System.DirectoryServices
	•	Direct LDAP queries

It does not heavily rely on dynamic PowerShell script blocks.

⸻

2.2 PowerShell Execution Policy Issue

Initially, script execution was blocked due to PowerShell execution policy restrictions.

To allow the script to run without permanently modifying system policy, PowerShell was launched with:

powershell.exe -ExecutionPolicy Bypass -NoProfile


Explanation:
	•	-ExecutionPolicy Bypass → Temporarily bypasses script restrictions for that session.
	•	-NoProfile → Prevents profile scripts from loading.

This allowed PowerView to be loaded using: . .\PowerView.ps1


2.3 Enumeration Commands Used

Since an older version of PowerView was used, enumeration relied on Get-Net* commands rather than newer Get-Domain* functions.

Examples:  
Get-NetUser
Get-NetGroup
Get-NetComputer
Get-NetLocalGroup


These commands query Active Directory using .NET directory services APIs.

⸻

2.4 Logging & Telemetry Analysis

Observations:
	•	No Event ID 4104 (Script Block Logging) was generated.
	•	No Event ID 4662 was observed during manual enumeration.
	•	However, Event ID 4688 (Process Creation) was logged.

Event ID 4688 Details:

Event 4688 recorded:
	•	powershell.exe execution
	•	Parent process relationships
	•	Command-line arguments (if enabled)

This highlights that:

Even when script block logging is not triggered, process creation telemetry remains visible.

⸻

2.5 Why Script Block Logging Did Not Trigger

The older PowerView version:
	•	Does not heavily use Invoke-Expression
	•	Does not generate dynamic script blocks
	•	Relies on .NET directory calls

As a result:
	•	PowerShell Script Block logging (4104) was not triggered.
	•	Enumeration occurred primarily at the LDAP/API level rather than script-block execution level.

⸻

Key Lessons Learned
	1.	Enumeration tools behave differently depending on implementation.
	2.	Not all PowerShell-based tools trigger Script Block logging.
	3.	LDAP monitoring (4662) can be more reliable than relying solely on 4104.
	4.	Process creation logging (4688) provides consistent visibility into PowerShell activity.
	5.	Version mismatches between SharpHound and BloodHound can cause data import errors.

⸻

Conclusion

This lab demonstrates:
	•	Automated graph-based enumeration using BloodHound
	•	Manual LDAP-based enumeration using PowerView
	•	The logging artifacts generated by each technique
	•	The limitations of relying solely on PowerShell script block logging

The exercise reinforced an important defensive insight:

Detection should focus on telemetry such as process creation and directory object access rather than relying exclusively on PowerShell logging.
